# PCL-CMU 魔改版 — Security Notes

Security posture of the local resource site + client harness, and the rules the
fork must follow.

---

## 1. TLS

* The resource server is **HTTPS-only**; the HTTP endpoint (`5080`) redirects
  (308) to HTTPS (`5443`).
* It binds **only to `127.0.0.1`** — it is never reachable from the LAN or from
  a wildcard interface.
* The default ASP.NET Core dev certificate covers only `localhost`, but the
  endpoint URL is `https://127.0.0.1:5443`. Therefore the scripts generate a
  **self-signed loopback certificate** whose SANs are `DNS:localhost`,
  `IP:127.0.0.1`, and `IP:::1`, and install it into the OS trusted store
  (`CurrentUser\Root`). This is the "self-signed cert trusted explicitly for
  localhost" path described in the plan.

  Setup commands:

  ```powershell
  # Canonical, for the default dev cert (covers "localhost" only):
  dotnet dev-certs https --trust

  # This package instead uses scripts/verify.ps1, which runs the equivalent of:
  #   ClientHarness make-cert --pfx resource-site/certs/loopback.pfx --cer resource-site/certs/loopback.cer
  # and then imports the .cer into Cert:\CurrentUser\Root (no UI).
  ```

* The client-harness **never disables certificate validation**. It relies on the
  OS trust store; the loopback cert is validated like any other TLS peer.
* If you cannot establish trust non-interactively, run
  `dotnet dev-certs https --trust` manually (or import the generated `.cer` into
  `Cert:\CurrentUser\Root`), and re-run `scripts/verify.ps1`.

---

## 2. Token separation

* The resource server and the auth/skin site (`csu-mc.magicalsheep.cn`) are
  **separate trust domains**:
  * Skin/auth site: handles Yggdrasil password login, user tokens, skins.
  * Resource server: serves **public** manifest/announcements/friends/pack/update
    data. It must never receive or store credentials.
* The fork must store auth tokens via `PCL.Core.Utils.Secret.EncryptHelper`
  (`SecretEncrypt`/`SecretDecrypt`, DPAPI-backed), **never** in plaintext JSON or
  in any `wwwroot` file.
* Never place a token in `state.json`, `manifest.json`, `latest.json`, or any
  file served by the resource server.

---

## 3. Path traversal

* The server rejects any decoded path or raw target containing `..` or the
  percent-encoded `%2e` (case-insensitive) with `404`.
* It checks **both** `Request.Path` (decoded) **and** `IHttpRequestFeature.RawTarget`
  so that literal `..` and `%2e%2e` are both caught regardless of server
  normalization.
* Directory requests return `404` (directory browsing is disabled).
* Unknown file types are not served (only explicitly-mapped `.mrpack`, `.bin`,
  and the standard static types).

---

## 4. Cache safety

* Immutable artifacts (`/packs/**`) are cached `public, max-age=31536000, immutable`.
* Volatile metadata is `no-cache`, so a stale revision or announcement can never
  be served from a client cache.
* `ETag`/304 and `Accept-Ranges: bytes` are enabled so clients can revalidate and
  resume without re-downloading whole artifacts.
* Security headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`) are applied to every response.
* No `Access-Control-Allow-Origin` is emitted (no CORS wildcard).

---

## 5. Signing key handling

* Signing uses **ECDSA P-256** over **SHA-256**; signatures are IEEE P1363
  (`r‖s`) base64.
* **Private key:** `resource-site/keys/update-signing-private.pem` — outside
  `wwwroot`, generated by `scripts/generate-keys.ps1`, and **excluded** from the
  package.
* **Public key:** `client-harness/update-signing-public.pem` — out-of-band with
  the client; never fetched from the same channel as the artifact.
* `scripts/sign-update.ps1` signs the artifact and writes `latest.json`; the
  private key is never written into `wwwroot` or into the zip.
* TLS certificate private keys (`.pfx`) live in `resource-site/certs/` and are
  likewise excluded from the package; they are regenerated per machine.

---

## 6. No secrets in JSON

`scripts/verify.ps1` scans every `*.json` under `wwwroot` for `token`,
`password`, `secret`, and `Authorization` and fails if any is present. The
shipped JSON contains none.

---

## 7. Production hardening (when moving off loopback)

* Replace the self-signed loopback cert with a CA-signed cert (Let's Encrypt /
  Cloudflare) and terminate TLS at the edge.
* Remove the HTTP→HTTPS redirect middleware (the edge handles it).
* Keep the same cache split and security headers at the CDN/edge.
* Move the signing private key into CI/secrets management; sign at release time
  and publish only `latest.json` + the public key.
* Serve packs from an object store (R2/S3) with `immutable` caching and
  `Accept-Ranges`.
* Add monitoring/alerting for unexpected 404/403 rates and for any attempt to
  probe traversal paths (`..`, `%2e`).
